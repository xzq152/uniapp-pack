# 04 · 实现要点

按模块记录「为什么这么做」，改代码前先看这一节能少走弯路。

---

## 1. 前端整包嵌进 exe（`go:embed`）

```go
//go:embed all:web/dist
var dist embed.FS
```

- `~/assets/` 带 hash 的文件加 `immutable` 长缓存；`index.html` 不缓存
- `/login` 也走 SPA（前端路由），所以服务端对非 API 路径统一回落 `index.html`
- **改前端后必须重新 `npm run build` + `go build`**，否则嵌入的还是旧页面（"改了没生效"多半是这个）

---

## 2. 进度推送用 SSE，不用轮询

`GET /api/jobs/{id}/events` 一条长连接推 `stage / progress / logs`；
列表页另有 8 秒轮询兜底（只在没有 SSE 连接时跑）。

> 副作用：页面开着 SSE 时，Chrome 无头截图会因为"永远不空闲"而超时。
> 自动化验证要用一次性页面或先关流（见 06-踩坑）。

---

## 3. 容器内怎么注入配置

`entrypoint.sh` 通过环境变量接收参数，`docker exec -e KEY=VALUE` 逐个传：

```
APP_ID / APP_NAME / APP_PACKAGE / APP_VERSION_NAME / APP_VERSION_CODE
KEYSTORE_FILE / STORE_PASSWORD / KEY_ALIAS / KEY_PASSWORD
APP_KEY / CHANNELS / USE_CN_MIRROR / GRADLE_EXTRA_ARGS
```

容器里做的事：

| 步骤 | 函数 | 说明 |
|---|---|---|
| 解包 | `maybe_unpack` | 支持 zip 和目录（目录会先压） |
| 找 www | `find_www` | 兼容 `__UNI__xxx/www`、`www` 等层级 |
| 注入资源 | — | `assets/apps/<appid>/www` |
| 图标 | `inject_icon` | 优先级：页面上传 > `config/branding/icon.png` > 包内 `static/app_icons` 最大图 > SDK 默认 |
| 启动图 | `inject_splash` | 不传就用 runtime 原生通用启动页；传了转 `.9.png` |
| appkey | `inject_appkey` | 写 `AndroidManifest` 的 `dcloud_appkey` |
| 渠道 | `inject_channel` | 写 `DCLOUD_STREAMAPP_CHANNEL` |
| 证书 | `prepare_keystore` | 页面传的 jks，或自动生成测试证书 `auto.jks` |
| 编译 | `gradlew assembleRelease` | 渠道多时按渠道循环 |
| 收集 | `collect_output` + `write_build_info` | 产出 `build-info.json`（含 apks 数组） |

## 4. 启动图：不要自己画位图

**结论来自拆官方云打包的 APK**：官方包里**没有任何 splash 资源**（没有 png、没有 .9、没有多密度图），
但装上去就是「圆形图标 + 加载动画 + 应用名」——说明那是 **runtime 原生渲染**的。

所以：

| 情况 | 行为 |
|---|---|
| 没传启动图 | 删掉模板自带的 `res/drawable/splash.png`，交给 runtime 画通用启动页（和官方一模一样，进度圈会动、适配所有屏幕） |
| 传了普通 png | 容器内 `NinePatch.java` 自动转 `.9.png`：检测内容包围盒，内容两侧打拉伸段，背景拉伸、内容锁定 |
| 传了 `.9.png` | 原样使用 |

DCloud 运行时绘制前会检查 `Bitmap.getNinePatchChunk()`，是 nine-patch 就用 `NinePatchDrawable`。
所以自定义图建议「纯色底 + 居中 logo」；全出血设计在比例差异大的屏幕上仍会整体缩放。

## 5. 渠道包

天猫/京东式的渠道包：一个版本，按渠道出多个 APK。

- Manifest 增加 `<meta-data android:name="DCLOUD_STREAMAPP_CHANNEL" android:value="包名|appid|0|渠道"/>`
- 官方是 `包名|appid|123911280508|huawei`，第三段看着是 DCloud 分配的包 ID，离线打包用不上，填 `0`
- 实现：工程只组装一次，之后**按渠道逐个 `assembleRelease`**（改 Manifest → 打包 → 收集）
- 时间：首个渠道 ~50s，之后每个 ~35s（Gradle 增量）
- 文件名插入渠道段：`容通助手_v2.3.1_huawei_20261109-110558.apk`
- 渠道名只保留 `[A-Za-z0-9_-]`，去重，上限 12 个

## 6. 清理策略（省磁盘）

| 对象 | 策略 | 触发点 |
|---|---|---|
| 上传的原包 | **构建成功即删**（失败保留以便重试） | 构建结束 |
| 孤儿上传 | 启动时清掉「没有 queued/running/failed 任务引用」的目录 | 服务启动 |
| APK 产物 | 只保留最近 **5 次构建**（`KEEP_APK`），更早的删文件、保留 `build-info.json` | 构建成功 + 启动 |
| 任务记录 | 只保留最近 **20 条**（`KEEP_JOBS`），更早的移入回收站 | 构建成功 + 启动 |
| 回收站 | 保留 7 天后彻底删除 | 启动 |

注意：APK 保留是按「**构建次数**」，不是按文件数——6 渠道 × 5 次 = 最多 30 个包（约 1.5GB）。

## 7. 下载

- 单文件：`GET /d/{jobId}/{文件名}`，支持 `Range`（断点续传 / 多线程下载）
- 整包：`GET /api/jobs/{jobId}/zip`，流式把该记录下所有 APK 打成一个 zip（`zip.Store`，不重复压缩）
- 中文文件名用 RFC 5987：`Content-Disposition: ...; filename*=UTF-8''<escaped>`

---

## 8. 托盘与无窗口启动

- `cmd/launcher` 用 `-H=windowsgui` 编译 → **PE 子系统就是 GUI，天生没有控制台**
- 拉起服务：`exec.Command` + `SysProcAttr{HideWindow:true, CreationFlags:CREATE_NO_WINDOW}`，然后 `Process.Release()`
- 托盘：`Shell_NotifyIconW` + 隐藏窗口收消息；`WM_LBUTTONDBLCLK` 开页面，`WM_RBUTTONUP` 弹菜单
- 单实例：`CreateMutexW("Local\\uniapp-pack-tray")`，重复双击只提示不重复启动
- 托盘图标：编译期 `go:embed tray.ico`（16/24/32/48/64 五尺寸），运行时写临时文件用 **`LoadImage`** 加载
  （细节和坑见 06）

## 9. 文件夹上传协议

浏览器不能直接传目录，所以把文件列表拼成一个流：

```
#F <相对路径>\n<字节数>\n<文件内容>
#F <相对路径>\n<字节数>\n<文件内容>
...
```

后端按同样格式流式还原成目录树（`safeRelPath` 防穿越），并写 `.folder-upload` 标记；
打包时服务端把目录压成 `packed.zip` 再送容器，容器端逻辑完全不变。
