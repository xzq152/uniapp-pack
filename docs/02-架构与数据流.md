# 02 · 架构与数据流

## 组件职责

```
pack-server（Go，单文件 exe）
├─ main.go      配置解析 / 路由注册 / go:embed 前端 / 启动时清理 / 静态资源服务
├─ api.go       全部 HTTP 接口：上传、建任务、日志、SSE、下载、证书、回收站
├─ build.go     一次打包的编排：准备配置 → docker cp → docker exec → 收集产物
├─ store.go     数据层：Job 结构、jobs.json 持久化、清理策略、回收站
├─ runtime.go   Docker 容器生命周期：检测 / 创建 / 启动 / 停止 / 重建
└─ auth.go      可选的访问口令（ACCESS_PASSWORD）

cmd/launcher（托盘宿主，GUI 子系统，无控制台）
  拉起 uniapp-pack-server.exe → 托盘图标 → 气泡提示 / 双击开页面 / 右键菜单
cmd/stopper
  发 WM_CLOSE 让托盘宿主优雅退出 → 兜底 taskkill

web（Vue3 + TDesign）
  表单 / 步骤 / 记录表 / 日志弹窗 / 进度条，构建产物被 embed 进 exe
```

**为什么拆成「服务」和「托盘宿主」两个 exe**：服务本身是控制台程序（调试时能看日志），
直接双击会留一个黑窗口。托盘宿主是按 `-H=windowsgui` 编译的，没有控制台，
由它用 `CREATE_NO_WINDOW` 拉起服务，用户只看到托盘图标。

## 一次打包的完整链路

```
① 上传          PUT /api/upload（zip 裸流） 或 /api/upload-folder（目录打包流）
                → data/uploads/<uploadId>/  （不解压，只读 manifest.json 填表单）
② 提交          POST /api/build → 生成 Job（queued）→ 进队列（单 worker 串行）
③ 准备配置      build.go prepareConfig：证书 / 图标 / 启动图 / 渠道参数 → data/tmp/cfg-<id>/
④ 送入容器      docker cp 资源包 → /workspace/src/
                docker cp 配置   → /workspace/config/
⑤ 容器内执行    docker exec -e APP_ID=... uniapp-pack-runtime /opt/pack/entrypoint.sh build
                  · 解压资源包，定位 www 目录
                  · 注入 assets/apps/<appid>/www
                  · 注入图标、启动图（.9.png）、appid/appkey、渠道 meta-data
                  · ./gradlew :app:assembleRelease（多渠道时按渠道循环）
                  · 收集 APK → /workspace/output/*.apk + build-info.json
⑥ 取回产物      docker cp 容器:/workspace/output/. → data/outputs/<jobId>/
⑦ 收尾          解析 build-info.json → 记录 sha256/签名/渠道列表
                删除原包（成功才删）、清理旧 APK、清理超出 20 条的旧记录
⑧ 前端          全程 SSE（/api/jobs/{id}/events）推 stage/progress/log，完成可下载
```

状态机：`queued → running → done | failed`。失败保留原包，记录上会出现「重试」；
成功则删原包，重试入口不再显示。

## 数据目录

默认 `pack-server/data/`（可用 `DATA_DIR` 指到别的盘；本机在 `D:\uniapp-pack-go\data`）

```
data/
├── uploads/<uploadId>/     上传的资源包（成功后即删，失败保留供重试）
├── outputs/<jobId>/        产物：APK 若干 + build-info.json
├── keystores/              jks + index.json
├── icons/                  页面上传的应用图标
├── splashes/               页面上传的启动图（.png / .9.png）
├── config/                 容器 /workspace/config 的镜像（含自动生成的 auto.jks）
├── trash/<jobId>/          回收站产物（记 7 天）
├── jobs.json               任务记录
├── appkeys.json            appid → DCloud 离线打包 appkey
└── trash/index.json        回收站索引
```

> `data/config` 是**跨构建持久化**的：证书、SDK 配置等留在里面复用。
> 但启动图属于「临时注入物」，进出这一层时会被主动剔除（否则会污染下一次构建）。

## 渠道包的数据形态

一条记录（Job）可以对应多个 APK：

```json
{
  "id": "j1794...",
  "versionName": "2.3.1",
  "channels": ["huawei", "honor", "xiaomi", "oppo", "vivo", "yingyongbao"],
  "apks": [
    { "channel": "huawei", "file": "容通助手_v2.3.1_huawei_20261109-110558.apk", "size": 53687091, "exists": true },
    { "channel": "honor",  "file": "容通助手_v2.3.1_honor_20261109-110558.apk",  "size": 53687091, "exists": true }
  ],
  "apk": "容通助手_v2.3.1_huawei_20261109-110558.apk"   // 兼容字段：第一个包
}
```

前端「下载」在有多个包时变成下拉：**全部下载（zip）** + 单个渠道。
`GET /api/jobs/{id}/zip` 会把这些 APK 流式打成一个 zip（Store 模式，不重复压缩），
所以 6 渠道只需要点一次，得到一个 `容通助手_v2.3.1_20261109-xxxx.zip`。
